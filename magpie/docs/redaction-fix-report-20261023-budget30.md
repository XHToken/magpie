# 脱敏问题与修复报告：30 秒预算及策略版本

日期：2026-10-23。范围：第三轮复测后的超时预算与策略声明修复。

## 本次决策

- 中文并列姓名漏检按 1.7B 模型能力限制保留记录，本次不继续修复。
- 模型返回位置越界、重复实体等无效结果时，继续阻断请求，不将原文发送云端。本次不增加重试或扩大解析容忍度。
- 将普通脱敏默认总预算从 15 秒调整到 30 秒；实验模式保持 30 秒。
- 将已有位置恢复行为写入策略声明，更新配置与验收标识。

## 问题一：长文本消耗完 15 秒总预算

第三轮样例包含 2,007 个字符：普通说明中夹有联系人与邮箱。在规则与模型组合检测路径中，文本按默认分块参数拆成两块并依次处理。1.7B、4B 分别在约 15,012 ms、15,001 ms 失败。

原限制是整次本地脱敏的预算，涵盖准备、排队和模型调用，多个分块共用一个截止时间。它不是云端回答生成超时。请求显式关闭思考模式；测试先加载模型并串行执行，未制造并发排队。原记录没有细分模型输入处理与逐 token 生成，因此不能将全部耗时归为输出生成。

15 秒限制分布在多个调用层，单独放宽外层会继续受到内层限制。

### 已实施修改

| 层级 | 修改后行为 |
| --- | --- |
| 运行时 Manager | 默认脱敏预算使用 `routerruntime.DefaultRedactionBudget`，统一为 30 秒 |
| 脱敏 Pipeline | 普通与实验模式的默认预算、最大预算均为 30 秒；显式更短预算仍有效 |
| RuntimeExtractor | 直接调用和经 Pipeline 调用均受 30 秒总截止时间限制；各批次不重新计时 |
| 严格策略 PrivacySpecification | `Budget()` 与策略记录的预算均为 30 秒 |
| 服务适配器 | 严格路径从策略读取预算；组合路径继续跟随 Manager 的预算 |
| 诊断回环与生命周期恢复 | 从策略读取截止时间，移除这几条路径中独立的 15 秒限制 |

调用方更短的截止时间、主动取消和失败阻断继续有效。模型输出 token 上限、输入上限和识别规则没有因预算放宽而扩大。Manager 的受信任测试调用方仍可以传入更短预算。

## 问题二：实际位置恢复行为与声明、指纹不一致

现有解析器已经允许有限的位置恢复：模型给出的起止位置必须先合法；如果该位置上的文本与返回实体不一致，仅在实体原文唯一出现、且通过 ASCII 边界检查时重新定位。

此前声明仍为 `coordinateRecovery:false`，解析器注释仍称禁止位置修正；普通策略还使用 `privacy-go-v5`。测试记录因而无法通过策略标识区分这次行为变更。

### 已实施修改

- 声明改为 `coordinateRecovery:true`，并明确 `coordinateRecoveryPolicy=unique-exact-substring-valid-coordinates-v1`。
- 普通策略升级为 `privacy-go-v6`，实验策略升级为 `privacy-trial-v2`；运行时实验入口同步只接受新的完整前缀与摘要。
- 预算与位置恢复策略都进入配置摘要，配置与验收套件指纹重新计算。
- 修正解析器注释，更新脱敏和本地运行时的设计文档。

这次只修正已有行为的声明，没有新增位置修正能力。越界位置、非原文实体、歧义定位、重复实体及其他无效结果仍拒绝。

模型、运行时文件、提示词和 JSON 结构没有变，不需要重新下载模型或升级外部依赖。新的策略标识不代表模型识别质量自动通过验收；新策略也不能继承旧策略的验收结果。

## 验证记录

证据目录为 `dist/redaction-budget30-20261023/`。全部真实模型样例均为合成数据，使用 Windows CPU、Spark-X2.5 Q4_K_M、llama.cpp b10828、65,536 上下文；未向真实云端发送样例。

### 真实模型复测

| 模型与场景 | 耗时 | 结果 |
| --- | ---: | --- |
| 1.7B，2,007 字长文本 | 18,581 ms | 完成；指定姓名和邮箱未残留，还原通过 |
| 4B，同一长文本 | 30,000 ms | `redaction_timeout`，继续阻断 |
| 1.7B，联系人与重音外文姓名两项 | 12,553 / 3,142 ms | 均完成，指定敏感值无残留，还原通过 |
| 4B，同上两项 | 13,329 / 3,491 ms | 均为 `redaction_invalid_result`，继续阻断 |
| 两种模型，版本号/端口/重试/百分比负样例 | 785 / 6,596 ms | 原样保留，还原通过 |

长文本的实际调用记录进一步确定了耗时位置：

- 1.7B 两块模型调用总耗时分别为 16,149 ms、2,413 ms；排队/加载记录为 0 ms、约 0.5 ms。
- 4B 第一块约 27,457 ms 完成；第二块开始后约 2,534 ms 到达整次请求的 30 秒截止时间，没有取得完整响应。
- 使用非流式请求，等待 HTTP 响应头的阶段包含服务端输入处理与输出生成；现有记录不能再将二者精确拆开。它不是排队或单独的思考阶段超时。

因此，首轮 30 秒复测帮助 1.7B 长文本完成，但该轮 4B 仍超时；后文保留隔离构建的第二次测量。两种模型实际记录的 `budgetMs` 均为 30,000。8 项组合测量只覆盖上述样例，不代替完整识别质量验收；采集程序退出 0 也不代表所有样例通过。
