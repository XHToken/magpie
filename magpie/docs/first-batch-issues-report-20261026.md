## 3. B1-01：默认明文观测的采集与保留边界未收口

### 3.1 当前行为及影响

服务在未注入独立观测存储时，默认打开 `<state>/redaction_observations.sqlite`。成功准备脱敏请求后，采集最新用户正文、脱敏后正文、类别和替换原值；未命中敏感信息的最新用户正文也可能被保存。当前没有用户侧的独立采集开关。

默认限额为 500 条、七天。关闭服务仅关闭数据库连接，不删除记录；管理接口清空后，后续符合条件的请求仍会继续采集。过期删除在数据库初始化、写入时执行，查询只按截止时间过滤，因此“页面不再显示”不等于“磁盘已经删除”。停写且不重启时，物理记录可能保存超过七天。

当前已有管理鉴权、POSIX 文件权限和 SQLite `secure_delete`。这些措施限制访问及辅助删除，但不等于用户已经选择保存明文，也不构成静态加密或严格的定时删除保证。

## 4. B1-02：组级脱敏 Manager 回退绕过能力准入

### 4.1 触发条件与调用链

触发范围是可信内部 `ModelOptions` 的一种组合：配置 `LocalRuntime.Manager`，提供 `RoutingOptions`，但没有设置 `Routing.LocalInvoker`；绑定组启用了本地脱敏，并进入云端准备路径。

当前链路为：组级脱敏 adapter → `groupLLMInvoker.Require` → Manager 回退返回 nil → `groupLLMInvoker.Invoke` → `Manager.Generate`。其中 `Generate` 是诊断/验收传输入口，不带正式能力 admission。正式 `Manager.Invoke` 会在开始前和实际执行时复查能力。

普通启动的显式 Manager 分支会转发前置 `Require`，不应把该问题描述为所有普通请求都绕过。不过，该分支随后同样直接使用 `Generate`，也应审查前置检查之后、排队或加载期间的能力失效窗口。

### 4.2 影响与证据

模型能力为 unknown、未获正式或可信实验授权时，该回退路径仍可能调用本地识别器。若得到格式合法的空实体结果，后续可能继续派发原文。这里描述的是能力检查缺口，不表示已经观察到真实用户信息外泄。

| 落点 | 问题 |
| --- | --- |
| [组级 adapter 构造](/D:/api-router/magpie/internal/routerservice/runtime_redactor.go:359) | 允许保留空 invoker 并使用 `LocalRuntime.Manager` 回退 |
| [Require/Invoke 实现](/D:/api-router/magpie/internal/routerservice/runtime_redactor.go:307) | Manager 回退 `Require` 直接成功；推理调用使用 `Generate` |
| [正式与诊断入口](/D:/api-router/magpie/internal/routerruntime/inference.go:176) | `Invoke` 有前置/执行时复查；`Generate` 传入 nil admission |
| [历史两平台复核](/D:/api-router/magpie/dist/review-20261022-round3/复核报告.md:7) | 历史候选已复现回退与显式分支行为不同 |

历史复现夹具的本地响应缺少当前严格解析要求的 `finish_reason` 等字段。当前候选应补成合法单候选完成响应后重跑，不能直接把历史 HTTP 200 当作当前已动态复现。

### 4.3 修复要求

1. Manager 回退必须执行相同目的的 `Require`，不能因 invoker 为空默认放行。
2. 正式业务推理使用保留执行时复查的入口；避免在前置检查后改走诊断入口。
3. 实验授权使用经可信启动选项授权、指纹和套件绑定正确的实验 invoker；不得通过宽泛放行恢复试用。
4. 明确自定义 invoker 的信任边界。测试假对象可以有专门契约，不能让缺少能力检查成为生产默认路径。
5. 检查材料/模型/后端发生变化后，旧能力和绑定是否在实际派发前失效。

### 4.4 必须补充的验收

| --- | --- |
| 显式 Manager，能力 unknown | 请求阻断，本地推理调用 0，云端调用 0 |
| Manager 回退，能力 unknown | 与显式路径一致，不得绕过 |
| 前置检查后能力撤销/绑定变化 | 真正执行前再次拒绝，云端调用 0 |
| 正式能力及绑定有效 | 正常抽取、替换并派发，合成敏感值不残留 |
| 实验启动未授权或绑定不匹配 | 拒绝；不能由业务 HTTP 请求自行取得实验权限 |

## 5. B1-03：路由组实际尝试次数与账本两次上限不一致

### 5.1 当前机制

路由组对每个成员调用 `BeginMemberDispatch`，重置成员尝试计数；每个成员最多两次不等于整次业务请求最多两次。跨成员回退及 patience 轮次会累计更多实际派发。现有 `TestGroupRoutingPatienceRetry` 使用前三次 429、第四次成功的场景。

但观测与账本仍沿用直连请求的两次上限：

- 事件观测忽略超过两次的尝试。
- 完成时只保留前两条 `AttemptDetails`，并把总数截为 2。
- 最终成功响应的 usage 写到被保留的末条尝试。
- 账本 `validOutcome` 拒绝 `Attempts > 2`；若末条保留记录仍为 `Retried=true`，还可能因“没有后继尝试”而校验失败。

这是源码可确认的契约冲突。本次没有新增端到端动态复现；具体写入失败及页面表现应由下列测试确认。

3. 对保留明细设置上限时，显式报告截断及真实总数，不能伪装为只有两次；最终成功尝试的身份与 usage 必须准确。
4. 失败尝试用量未知时保持未知，不将最终成功用量复制到其他尝试，也不自行推算重试账单。
5. 如持久化契约需要变化，按 schema/migration 规则处理已有数据；不得删除旧账本或把缺失明细补成虚构记录。
