# CPU/GPU 推理后端自动选择方案

日期：2026-10-23。本文保留当时的设计与现状分析。2026-10-24 已完成首轮接入，当前行为与实测范围见[实现与验证报告](gpu-runtime-implementation-report-20261024.md)；下文“当前项目”指方案提出时的版本。

## 1. 目标与建议

让同一个应用根据本机可用驱动、已校验运行包、当前可用显存和实际加载结果，自动使用 CPU、GPU 或 CPU/GPU 混合推理。默认自动选择；显卡不可用时仍可在满足内存要求的机器上使用 CPU。

建议先交付 Windows x64 的 NVIDIA CUDA、AMD/Intel/NVIDIA Vulkan 和现有 CPU 回退，之后完善 Apple Silicon Metal 与 Linux 实机覆盖。首轮不引入多 GPU 分片、动态更换模型或自动降低上下文。

核心原则是：**有显卡只代表存在候选设备；驱动可用、模型实际卸载到 GPU、负载测试通过后，才能报告 GPU 加速生效。** GPU 加速改善处理耗时，不代表脱敏漏检、位置越界或重复实体问题自动解决。

## 2. 当前项目为什么没有自动加速

以下结论来自当前源码，而非仅依据设计文档：

| 当前位置 | 实际行为 | 本次设计需要补充 |
| --- | --- | --- |
| `routerdevice/native_windows.go`、`probes.go` | 读取 RAM、DXGI 显卡信息；CUDA/Vulkan 后端返回 unknown | 增加驱动与后端可用性证据，补充实时内存预算 |
| `routermanifest/manifest.go` | Windows/Linux 固定 CPU 包；macOS arm64 有 Metal 包 | 增加固定版本 GPU 运行包、依赖和兼容性元数据 |
| `routerruntime/storage.go:PlatformRuntime` | 按 OS/架构取得首个匹配项 | 改为明确的候选选择器，不能依赖目录顺序 |
| `routerservice/local_models.go` | 构造 Manager 时固定 RuntimeID | 让 Manager 持有后端候选与有效执行计划，支持受控回退 |
| `routerprocess/process.go:arguments` | CPU 显式设置 `--n-gpu-layers 0`；其他后端未显式规划 GPU 层数/设备 | 用强类型启动计划指定设备和卸载层数 |
| `routerprocess.NativeFactory.Start` | stdout/stderr 均丢弃；健康检查只证明 HTTP 服务可用 | 增加不含用户原文的实际后端、卸载层数和内存证据 |
| `routerprocess/dependency.go` | Windows 依赖按现有 VC 集合校验，统一版本、单文件 64 MiB 上限 | 将 VC 与 CUDA 等独立依赖集区分，按实际文件校验 |
| `routerruntime/types.go:Status` | 没有“请求后端/实际后端/回退原因”的完整字段 | 补充后端状态与可解释结果 |

现有模型推荐中的“6 GiB 独显”是推荐启发式，不能直接作为“4B + 64K 上下文必然可装入 GPU”的判断。

## 3. 自动选择规则

### 3.1 平台候选表

表中箭头表示有界的候选回退顺序，不代表每次启动都下载、加载并跑完全部候选。

| 硬件与系统 | 默认候选 | 选用条件 |
| --- | --- | --- |
| Windows x64 + NVIDIA | CUDA 12.4 → Vulkan → CPU | GPU 架构被发布包支持，驱动与依赖可用，固定模型/上下文加载及卸载验证通过 |
| Windows x64 + AMD 独显 | Vulkan → CPU | 通过该运行包要求的 Vulkan 计算功能、内存与加载检查 |
| Windows x64 + Intel Arc | Vulkan → CPU | 与 AMD 相同；不因品牌直接认定支持 |
| Windows x64 + 核显 | CPU；已认证设备可试 Vulkan | 使用共享内存预算与实测；共享内存不计作独立显存，不保证比 CPU 快 |
| Apple Silicon | Metal → CPU 候选 | Metal 实测可用，统一内存足够；CPU 回退须补充并验证对应运行方式 |
| Linux x64 | 已验收 CUDA/Vulkan → CPU | 单独验证驱动、动态库与实机；不能用 Windows 结果代替 |
| 未识别显卡、驱动失败、软件/远程适配器 | CPU | CPU 与系统内存检查通过；保留 GPU 不可用原因 |
| 不支持的 OS/架构，或 CPU 也无足够内存 | 不加载 | 返回明确不可用原因，不伪装为 CPU 已就绪 |

NVIDIA 首批优先验证 CUDA 12.4，原因是缩小首轮依赖和兼容性矩阵；CUDA 13.x 后续按 GPU 架构与发布包实测加入，不能假设所有新旧 GPU 都适合同一 CUDA 包。AMD 的 ROCm、Intel 的 SYCL 可作为后续优化后端，不列入第一阶段必须项。

上述路线依据 llama.cpp 的后端支持与现有 b10828 发布资产制定，实际可用性仍由本机验证决定。[b10828 后端构建说明](https://github.com/ggml-org/llama.cpp/blob/b10828/docs/build.md)

### 3.2 决策算法

```text
如果用户明确关闭本地模型：保持关闭，不启动探针负载或模型
读取已选模型、系统与硬件事实，不改动模型选择
按 OS、驱动能力、运行包兼容性产生 GPU 候选，CPU 始终作为已支持平台的末选
对候选逐个执行：
    确认运行包已安装且校验通过；未安装时按第 5 节处理
    核验设备身份与当前内存预算
    在保持模型、64K 上下文、量化与单槽不变的前提下制定卸载计划
    无可行计划则跳到下一候选
    使用 Manager 生命周期启动唯一模型子进程
    检查健康、实际设备/卸载层数、完整 JSON 合成推理和取消释放
    通过后发布有效计划、生成新执行身份并运行原有能力检查
    失败则回收自己启动的进程，记录原因，按有界策略回退
没有候选通过：模型不可用；脱敏请求继续阻断
```

自动模式不能因为 GPU 不满足 4B 的完整卸载，就擅自把用户选定的 4B 改成 1.7B。模型推荐仍由现有逻辑负责，后端选择处理“这一个模型如何运行”。

## 4. 检测：区分硬件、驱动与实际运行

### 4.1 三层证据

| 层级 | 需要的事实 | 不能据此声称的结论 |
| --- | --- | --- |
| 硬件层 | 厂商、设备 ID、专用/统一/共享内存类型、物理内存、可用 RAM | 有 NVIDIA 名称不等于 CUDA 可用 |
| 驱动/运行包层 | 设备可枚举，驱动可初始化，发布包兼容，所需功能可用 | `--list-devices` 成功不等于模型有 GPU 卸载 |
| 模型执行层 | 指定设备，实际卸载层数/缓冲区，健康、合成推理、耗时与取消结果 | 显存占用上升、HTTP 200 或“加载成功”都不等于正式识别质量通过 |

在 `routerdevice` 保持现有只读边界：不下载、不跑模型、不调用进程。增加 `VendorID`、设备 UUID/LUID/PCI 标识、驱动版本、计算功能、专用/统一内存类型、可用预算、采样时间和来源；unknown 仍为 unknown。

需要初始化驱动、创建计算上下文或运行已校验二进制的测试放到 `routerruntime` 协调的受控探针中，使用 `routerprocess` 的进程归属与取消机制。建议做独立 `cmd/runtime-backend-probe`，输出固定、限长 JSON；例如 `--probe=cuda|vulkan|metal`。不让厂商驱动错误带崩主服务，超时可回收。

Windows CUDA 探针通过驱动 API 检查初始化、枚举与实际上下文创建，读取计算能力和当前可用显存；不能要求用户必须安装 `nvidia-smi`，也不能仅以 DLL 存在、CUDA Toolkit 存在或 `nvidia-smi` 的版本字符串作为通过证据。驱动支持范围和运行包要求需要同时核验。[NVIDIA 驱动初始化](https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__INITIALIZE.html)、[CUDA 兼容性说明](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html)

Vulkan 探针实际枚举设备、计算队列和运行包需要的特性，并创建逻辑设备。显存预算优先读取 `VK_EXT_memory_budget`，其预算随其他进程占用变化；缺失该扩展时标记估计来源，采用保守预算并依赖加载验证，不以显存总量代替实时可用量。[Vulkan 内存预算](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_memory_budget.html)

Metal 读取设备和推荐工作集/当前分配情况；统一内存与系统 RAM 是同一资源池，不能相加。当前 no-cgo 路径对 Metal 为 unknown，必须补齐系统原生桥接或受控探针，不能只因为机器是 Apple Silicon 就标记通过。

### 4.2 多显卡与重新检测

首轮单设备运行，不累加不同 GPU 的显存，也不启用多卡分片。按可用预算、兼容性和历史验证结果选择，设备索引通过稳定标识映射；不能默认第 0 张就是独显。核显不得挤掉已验证的离散 GPU。

普通状态 GET 只返回最近快照，不反复初始化 GPU。用户启用本地模型、应用启动恢复、显式“重新检测”、驱动/设备变化或加载失败时，才做需要的重新检测；每次正式加载前刷新内存预算。失败缓存按硬件、驱动、运行包、模型与上下文区分，初始建议 10 分钟冷却，可手动重试。

## 5. 固定运行包与安装

保留 b10828 和现有 GGUF，避免首次接入同时更换推理引擎版本与模型。官方该版本已列出 Windows CUDA 12.4、CUDA 13.3、Vulkan 以及配套 CUDA DLL 包；其中 CUDA 运行包与依赖可能是分开的资产，不能只下载 EXE。[b10828 发布资产](https://github.com/ggml-org/llama.cpp/releases/expanded_assets/b10828)

建议新增候选 RuntimeID：`windows-amd64-cuda12`、`windows-amd64-vulkan`；CPU ID 保持。每个候选独立目录，复用同一模型与模板文件，避免复制下载模型。

每个目录的清单必须锁定：源码提交、下载 URL、精确字节数、压缩包 SHA256、展开上限、逐依赖文件 SHA256/架构、实际支持的 GPU 架构和驱动约束。实施时下载并校验原始包、确认再分发许可；网页显示的摘要只是前期线索，不等于文件验收。

必须同步改造当前限制：

- `Artifact.ExpandedBytes` 不能继续给所有包统一使用 256 MiB，GPU 包及依赖需要逐包测量并设置有界上限。
- 安装空间按所选模型与后端组合计算，覆盖依赖、压缩缓存、展开、原子替换、损坏隔离副本和 CPU 回退包；不能只复用模型现有固定余量。
- Windows VC、CUDA 等依赖需要独立集合，不强制所有 DLL 的文件版本相同；保留逐文件哈希与架构校验。当前单依赖文件 64 MiB 上限也要按已核验 GPU 包调整，不能无界放开。
- DLL 从应用私有、已验证的目录加载；操作系统驱动库使用受控系统搜索。不得从任意当前目录或继承 PATH 选择 GPU 运行库，不改全局 PATH、不自动安装/升级显卡驱动。
- 各后端有独立安装收据；模型文件存在不能被误报成 GPU 运行包已安装。

下载纳入既有安装/启用本地模型的操作流程，不要求用户手工选 EXE。可用 CPU 包保留作为回退。普通启动只使用已经安装并校验的后端；发现 GPU 包缺失时可先继续 CPU，并显示“可安装 GPU 加速组件”。安装动作可自动选包和补齐组件；普通状态查询、探针及业务请求不得触发隐式下载。

## 6. 显存规划与启动参数

### 6.1 不能只看模型文件大小

按固定模型、64K 上下文、单槽、实际 KV 类型和 batch 估算：

```text
GPU 所需内存 = 卸载权重 + 放在 GPU 的 KV/模型状态 + 计算图/工作缓冲区 + 后端开销
GPU 可规划预算 = 当前可用设备预算 - 桌面/其他应用余量
```

初始余量建议取 `max(1 GiB, 设备总显存的 15%)`，随后由实机数据校准；这是产品建议值，不是所有显卡的保证。内存估算结合 GGUF 的真实结构和运行时报告，不能套用通用 Transformer 公式后声称 Spark 模型实测内存。

Apple/核显使用共享预算，保留现有系统可用内存保护，GPU 与 RAM 占用避免重复计算。同样不能把“集显显示 16GB 共享显存”当成 16GB 可用独显。

### 6.2 执行计划

新增强类型 `BackendPlan`，至少记录：`runtimeID`、`backend`、稳定 `deviceID`、`offloadMode`（none/partial/full）、请求/有效 GPU 层数、KV 放置、context、batch/ubatch、规划预算、策略版本和选择原因。首轮固定 KV 精度与 batch 基线；如改变它们，另做策略版本与质量验收。

| 条件 | 计划 |
| --- | --- |
| 固定上下文的完整 GPU 放置有余量 | 全部可卸载层放 GPU |
| 完整放置不足，存在经验证的部分卸载方案 | 部分层 GPU，其余 CPU；页面明确显示“混合推理” |
| 预算未知且无法验证，或部分卸载无收益/无法加载 | 选择下一个候选或 CPU |
| CPU 也不满足内存条件 | 不加载，明确原因 |

不得悄悄把 64K 降为 8K 来“成功启动”。上下文调整属于独立用户可见策略；此次后端接入保持现有上下文和 30 秒脱敏总预算。

llama.cpp b10828 提供设备选择、卸载层数、单卡划分和自动适配等参数。生产启动应显式下发已验证计划，例如设备、正整数 GPU 层数、单卡模式；CPU 明确设置 GPU 层数为 0。自动适配不得产生未记录的上下文或内存策略变化，计划确认后使用明确参数并验证实际结果。[b10828 服务参数](https://github.com/ggml-org/llama.cpp/blob/b10828/tools/server/README.md)

把这些设置放进 `routerprocess.Spec` 的受信任字段，不通过 HTTP 的任意命令行或宽泛 `ExtraArgs` 注入。继续固定 loopback、单槽、模型、模板与本地文件；清理能覆盖后端/设备/卸载策略的继承环境变量。

### 6.3 验证真正加速

启动时从固定版本运行时取得设备、实际卸载层数和内存分配的结构化事实；若该版本无完整 API，可在仅启动阶段消费限长日志并白名单提取字段，无法识别则 unknown。禁止把完整 stderr、用户提示词或响应永久写日志。

`healthy=true` 和 `accelerated=true` 分开。GPU 必须有匹配设备与有效非零卸载的证据，并通过固定合成推理，才能标记 accelerated。GPU 包实际回落到零层 CPU 时标为 CPU/验证失败，不能显示 GPU 已启用。

弱核显或部分卸载可能不比 CPU 快。默认只启用已认证硬件配置；未知配置在启用/诊断阶段做小规模 CPU 对照，未验证收益时保留 CPU。建议加速选择参考门槛为合成工作负载中位耗时改善至少 20%，此数值待验证；不要每次启动、每个请求都跑双份基准。

## 7. 生命周期、回退与指纹

### 7.1 生命周期归属

保持一个 Manager 和一个模型进程。候选启动、停止、卸载、崩溃恢复都通过现有进程所有权机制；停止并确认旧子进程退出后，才能加载下一候选，不使用两个完整模型并行抢占内存。

建议 Manager 增加 `PrepareBackend/ActivatePlan` 内部操作，更新当前有效 RuntimeID，而非到处改写 `Options.RuntimeID`。切换时暂停新准入，完成或取消旧调用、排空槽位、回收旧进程、发布新 epoch、重新校验能力。`SnapshotBinding` 在同一锁内取得运行时、模型、设置与执行计划，防止混合新旧身份。

不在请求执行中来回切后端。用户关闭、服务关闭和取消优先，不能因自动恢复重新启用用户已关闭的模型。

### 7.2 有界回退

| 失败 | 处理 |
| --- | --- |
| CUDA 驱动/架构不兼容 | 跳到已安装、已验证的 Vulkan，否则 CPU |
| GPU 内存不足 | 同一后端最多尝试一次保守部分卸载；仍失败则 CPU |
| GPU 健康但实际卸载为 0、证据不明 | 不报告加速，选择可验证后端 |
| 原生 GPU 进程崩溃/设备丢失 | 回收进程，冷却该候选，安全切下一后端 |
| 请求取消/上层期限耗尽 | 立即结束该请求，不为回退刷新截止时间 |
| 模型返回越界位置、重复实体、坏 JSON | 保持无效结果阻断；这不是换 GPU/CPU 重跑的触发条件 |
| 模型/依赖文件损坏 | 不执行损坏包；记录修复原因，只有独立已校验候选可参与回退 |

初始建议一次激活最多 3 次模型加载尝试，总计共享现有加载截止时间；不是每换后端再给一轮完整 90 秒。所有单项探针也受剩余加载时间约束，取消可随时打断。卸载/回收有独立短期限。

已开始的脱敏请求在 GPU 失败时默认安全失败；下一请求可使用恢复后的 CPU。若将来增加当前请求重试，必须仍在原 30 秒总预算内且输出尚未提交，不能后台自动转云并携带未脱敏原文。硬件故障后的能力检查未通过前，不能复用旧后端的验收结果继续放行。

### 7.3 身份与缓存

现有 `Model.Fingerprint(Runtime)` 已包含 Runtime 元数据，换固定包会变更指纹，但尚未完整覆盖设备与实际卸载参数。建议新增版本化执行身份：

```text
executionIdentity = hash(
    runtimeArtifact + dependencySet + backend + deviceCompatibilityKey + driverVersion
    + modelArtifact + templateArtifact + effectiveContext
    + effectiveGpuLayers + kvPlacement + kvTypes + batchProfile + selectorRevision
)
```

将执行身份接入能力门禁、路由绑定、脱敏缓存与观察记录。实际内存余量、GPU 温度和单次耗时不进缓存身份，避免每次采样都失效。显示选择原因与动态指标不等于更新执行计划。

GPU 换包、驱动变化、实际卸载方案改变时，旧能力结果失效、旧 pipeline 退休；已准备响应的独立还原快照保留到请求结束。推理后端变化不要求重新下载模型，也不应改写宿主 endpoint、云端 provider 或用户选定模型。

## 8. 页面和诊断

默认自动，用户无需配置 CUDA 参数。可提供“强制 CPU”和“重新检测”作为可回退的高级操作；第一阶段不开放任意 GPU 层数/设备命令行。

页面显示真实、便于判断的信息，例如：

- `GPU 加速：NVIDIA … / CUDA`，实际卸载 `N/M` 层，模型和有效上下文。
- `混合推理：GPU + CPU`，显存不足而采用部分卸载。
- `CPU 推理：GPU 驱动不兼容`，或 `GPU 加速组件尚未安装`。
- `GPU 计划待验证`，不得用“检测到显卡”替代“加速已生效”。

状态 API 建议补充 `requestedBackend`、`effectiveBackend`、`runtimeID`、`adapterName`、`accelerationState`、`offloadedLayers`、`memoryBudget`、`fallbackReason`、`planRevision`、`checkedAt`。设备完整 UUID 与本机路径只留本地受控诊断，页面仅显示必要信息。

在现有 `diagnose-local` 增加后端检测、CPU/GPU 对照和输出证据选项；普通诊断不得自动切换运行中的正式服务。实际参数名在实施时统一，避免另造一套不走 Manager 的测试引擎。

## 9. 实施任务与顺序

| 阶段 | 主要改动 | 完成标准 |
| --- | --- | --- |
| A：设备与可用性 | `routerdevice`、受控 backend probe、新事实结构 | GPU/驱动/内存 unknown 与 unavailable 区分；设备身份匹配 |
| B：运行包 | `routermanifest`、`routerdownload`、`routerruntime/storage.go`、Windows 依赖装配 | 固定 CUDA12/Vulkan/CPU 组合验证，缺包和空间不足可解释 |
| C：选择与加载 | 新 `routerruntime/backend_selector.go`、`backend_plan.go`；Manager 和 `routerprocess.Spec` | 自动选择、显式设备/层数、实际卸载证据、有界回退、无孤儿进程 |
| D：业务集成 | `routerservice/local_models.go`、能力检查、路由身份、脱敏 pipeline | 使用真实有效计划，后端切换失效缓存并重验能力，保持 30 秒总预算 |
| E：页面与诊断 | 本地模型页面、五语言状态说明、`routeracceptance` | 页面事实与原生证据一致，可导出 CPU/GPU 对照报告 |
| F：跨平台 | Apple Metal/no-cgo 检测补齐、Linux 实机 | 每个平台原生测试，不能只跨编译 |

A—E 组成 Windows 可交付闭环。可以先用 NVIDIA 实机完成 CUDA 路径，再在 AMD/Intel 实机完成 Vulkan；尚未实测的设备组合不能默认为已认证。方案本身不修改现有运行服务。

## 10. 验收计划

### 10.1 自动化测试

用可注入设备快照、假进程与固定响应覆盖：无显卡、缺驱动、旧驱动、不支持计算架构、核显共享内存、双显卡索引错配、显存不足、显存查询失败、GPU 启动成功却零层卸载、显存 OOM、GPU 崩溃和用户取消。验证每项都选择正确后端且保留真实失败原因。

校验安装路径、文件哈希、单独依赖集、压缩展开上限、下载中断与空间不足；GPU 包损坏不能执行，也不能覆盖已可用 CPU 安装。测试运行时切换的 epoch、缓存、快照、队列释放、关闭和重复启动；并发状态读不得阻塞卸载。

脱敏安全回归继续检查：13 项历史无效结果零出站、正常结果可发送、JSON/SSE 还原、30 秒总期限不续期、更短调用方期限生效。GPU 后端不能绕过任何解析和质量门禁。

### 10.2 实机矩阵与判定

| 机器类型 | 期望 |
| --- | --- |
| 无独显 Windows | 自动 CPU，现有能力不倒退 |
| NVIDIA 不同显存档、现代及较旧架构 | 兼容时 CUDA；不兼容/不足时部分卸载或解释性回退 |
| AMD 独显、Intel Arc | Vulkan 实际卸载验证与性能对照 |
| 只有核显/显存被其他应用占用 | 不误报专用显存，不频繁切换，未知/无收益时 CPU |
| 双显卡笔记本 | 选择验证过的正确设备，不假设序号 0 |
| Apple Silicon、Linux GPU | 各自平台原生验证后开放 |

每个要发布的组合记录 GPU 型号、驱动、后端、运行包/模型摘要、实际层数、KV/上下文、加载时间、显存峰值、输入处理与输出速度、排队/总耗时，以及失败类别。GPU 利用率仅辅助，不作为加速已生效的唯一依据。

保持同一模型、量化、提示词、样例和 64K 上下文做 CPU/GPU 对照：热启动后至少 30 次原长文本及多字段请求，冷启动至少 3 次，再做 2/4 并发、取消与其他应用占显存测试。单槽并发请求仍会排队，GPU 不等于自动支持多槽。

建议正式纳入自动选择的性能门槛：长文本/多字段样例热态成功率 30/30，P95 不超过 24 秒，为 30 秒总限额留余量；目标硬件需体现实际收益。门槛是建议验收值，不是已测结论。若 GPU 仍靠近 30 秒，需要优化输入/批次或评估更快硬件，不能只因为显示 GPU 就宣称问题已解决。

识别准确率独立统计：漏检、误检、无效结果、超时分别计数。CPU/GPU 数值差异可能影响结果，应重跑原语料；不能要求输出逐字一致，也不能把少超时等同于模型本身识别质量提高。

## 11. 当前证据边界

本方案已核对项目相关源码、现有设计与 llama.cpp b10828 官方参数/发布列表；没有安装 GPU 组件、修改驱动、执行 GPU 原生测试，也未测出任何显存档的保证值。下载包的精确字节数、展开量、依赖逐文件清单和 GPU 架构覆盖需在 B 阶段补齐并实测。

最近 CPU 脱敏测试中，4B 原长文本一次在 30 秒超时、一次约 29.3 秒完成，为本方案的性能动机；这些数字不能用来预测特定 GPU 的倍速。

后端切换仅处理本机推理进程，保持普通启动入口、应用/provider/模型设置与 WorkBuddy/Loomy endpoint；不通过修改宿主地址去连接另一测试实例。
