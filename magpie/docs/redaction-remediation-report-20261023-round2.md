状态：部分修复，待继续修改及验收\

## 1. 当前结论

最优先的卡点仍是“识别结果不可信时，系统没有始终阻断上游发送”。原来的坏 JSON、截断等 7 个样例已经通过，但 6 个新的结构或语义异常样例仍被当成成功，模拟云端收到了未脱敏姓名。

此外，严格识别质量、姓名规则误伤、复杂输入耗时均未完成验收；产品固定诊断入口还存在模型指纹与上下文配置不一致的问题。

本轮仅整理修复任务，不修改产品代码、不重新运行模型测试。以下结论对应已经完成的第二轮复查候选，后续改动必须复测。

## 4. 第一批：补齐失败阻断

### F-01：结构合法不等于识别完整

**代码入口。** [detector_llm.go](../internal/routerredact/detector_llm.go) 的 `ParseLLMContentStrict`，当前参考行 445、471、478、485；以及 `parseLLMEntitySliceStrict`。

**问题。** 目前看到 `entities` 或 `findings` 就解析列表并返回；忽略 `complete:false` 等其他字段。`fields:[]` 也能变成成功空结果；通用 JSON map 解码会覆盖重复键，无法在解码后识别原始重复内容。

**已复现的模型内容。** 下列内容均被放入合法、`finish_reason=stop` 的模型响应中：

```json
{"complete":false,"entities":[]}
```

```json
{"complete":false,"fields":[]}
```

```json
{"entities":[{"label":"NAME","value":"宁祁"}],"entities":[]}
```

输入为合成文本：

```text
本段内容是宁祁以及陆遥的内部记录，电话13812345678。
```

实际返回 HTTP 200、模拟上游调用数 1，上游捕获到姓名原文。该输入没有使用新增姓名规则中的“请转告”等触发词，避免规则兜底掩盖校验缺陷。

**需要修改。**

1. 明确支持的输出契约，使用相同契约构造提示词、输出 schema 和解析器。
2. 如果契约只有 `entities`，则拒绝未声明的 `complete`、`fields` 等键；如果要兼容这些字段，就完整验证其语义，`complete:false` 必须拒绝。
3. 在 JSON 解码边界拒绝重复键，不能先覆盖成 map 再校验。
4. 若支持字段列表，则验证编号、唯一性、字段数量及覆盖情况；不能将缺失字段、空字段覆盖当成“没有敏感实体”。
5. 拒绝互相冲突的列表别名或结构。合法空实体列表应有明确语义，不能与无法解析混用。

**验收。** 上述异常样例全部返回失败，上游调用数为 0；合法完整空实体与合法完整非空实体两个对照仍可正常发送。原 7 个异常样例不得回归。

### F-02：敏感实体定位失败不能被静默过滤

**代码入口。** [detector_llm.go](../internal/routerredact/detector_llm.go) 的 `detectChunk`（当前参考行 248、252）、`alignAndFilterEntities`（1049）和 `ResolveEntitySpans`。

**复现。** 对同一合成输入返回：

```json
{"entities":[{"label":"NAME","value":"原文里不存在的姓名"}]}
```

实际仍返回 HTTP 200、模拟上游调用数 1，姓名原文未替换。标签和值通过解析后，定位函数找不到匹配，实体被丢弃；编排器仍将剩余结果声明为完成。

**需要修改。**

1. 区分“策略允许透传的标签”和“敏感实体无法定位”，后者必须报错。
2. 让实体对齐阶段返回可传播的错误或完整性状态，避免只有一个过滤后的列表。
3. 敏感候选必须能对应到原文精确子串及合法 UTF-8 字节边界；重复内容需有明确处理规则。
4. 一条敏感候选无效时，不能保留其他候选后宣告整段识别完成。确需重试，必须在同一总预算内重新取得完整有效结果。
5. 明确空白规范化等宽松匹配是否属于契约；不要把模糊对齐作为隐式“修复成功”。

**验收。** 不存在于原文的敏感实体必须阻断。补测“一个有效实体＋一个无效实体”、重复姓名、emoji、重音字符及边界冲突，验证不会部分放行，也不会破坏合法映射和还原。

### F-03：外层响应仍允许不完整或有歧义的结果

**代码入口。** [detector_llm.go](../internal/routerredact/detector_llm.go) 的 `extractCompletionTextStrict`，当前参考行 399、410、417。

**问题与复现。** `choices` 只检查非空，`finish_reason` 允许缺失或空字符串。以下两类响应均已复现 HTTP 200、模拟上游调用数 1，并捕获姓名原文：

- 两个 choices：首项是空实体结果，第二项标记 `length` 截断；解析只取首项。
- 一个 choice：content 是空实体结果，但未提供结束原因。

**需要修改。**

1. 对当前单结果请求要求恰好一个候选，检查需要的候选编号和消息角色。
2. 只接受契约约定的完成状态；拒绝缺失、空值、截断、工具调用或其他非抽取结束状态。
3. 校验拒答、推理内容、内容块和截断标记等会影响完成语义的字段，不能只拼出一段非空 text 就认定成功。
4. 若要兼容不同格式，应分别定义、验证，不应自动把缺字段视为正常。
5. 现有模拟响应若缺少真实模型会返回的字段，应修正夹具；不要为了让旧夹具通过而放宽真实完成性要求。

**验收。** 两类新样例必须阻断；同时补测 `length`、`tool_calls`、拒答、多个候选和不支持的内容块。正常单候选完成结果继续通过。

## 5. 第二批：恢复有效验收，再修改识别协议

### V-01：固定诊断没有使用实际上下文绑定

**代码入口。** [privacy.go](../internal/routeracceptance/privacy.go) 的 `runPrivacyRepairDiagnostic`，当前参考行 195；参照 [settings.go](../internal/routerruntime/settings.go) 的 `Manager.SnapshotBinding`，以及 [runtime_redactor.go](../internal/routerservice/runtime_redactor.go) 的生产规格构造路径。

**已确认事实。** 当前运行时默认上下文为 65,536，诊断规格仍按固定模型默认 8,192 构造模型指纹。内置 full 诊断的 56＋10 条语料全部为 `redaction_unavailable`，实际生成调用数为 0；JSON/SSE、工具和生命周期组合检查在状态/指纹检查处被拦截。

这属于诊断入口失配，不代表所有生产脱敏请求都发生同样故障，也不能作为识别准确率数据。

**需要修改。**

1. 从同一 Manager 快照读取实际模型、运行时、指纹及上下文设置，构造诊断规格。
2. 在开始评测前核对绑定；不匹配应明确报告诊断前置条件失败，而不是生成一整套“零调用的模型质量结果”。
3. 审查工具 roundtrip、生命周期与其他诊断分支是否也按旧上下文计算指纹。
4. 保持 capability 为 `unknown`，不通过绕过指纹、伪造验收或自动开启实验权限来使诊断变绿。

**验收。** 在支持的上下文配置下验证规格与实际 Manager 指纹一致；66 条中应执行推理的样例确实产生调用记录，预期输入限额样例可在调用前拒绝。工具、JSON/SSE、取消恢复、短 deadline 检查必须真正执行并记录结果。另保留故意错配配置的拒绝测试。

### R-02：严格抽取的位置协议仍不可靠

**代码入口。** [privacy_specification.go](../internal/routerredact/privacy_specification.go) 的 `Build`、`Batches`；[privacy_parse.go](../internal/routerredact/privacy_parse.go) 的 `PrivacySpecification.Parse`；[runtime.go](../internal/routerredact/runtime.go) 的 `RuntimeExtractor`。

本轮通过独立隔离探针绑定实际 65,536 上下文，再调用相同 Manager 和严格评估器，取得了有效测量：

| 语料 | 预期实体 | 正确实体 | 误检 | 漏检 | 精确率 | 召回率 | 阻断请求 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 固定56条 | 55 | 16 | 16 | 39 | 50.0% | 29.1% | 20 |
| 留出10条 | 11 | 4 | 1 | 7 | 80.0% | 36.4% | 2 |

固定语料包含18条无效结果、1条超时、1条预期输入限额阻断；留出语料包含1条无效结果、1条超时。本轮补充探针只记录了公共错误类别，没有保存细分解析原因，不能将全部无效结果均归为某一种坐标错误。严格协议仍要求模型返回位置，尚未取得该问题修复通过的证据。

指标为标签与实体匹配口径，包含允许透传标签，且阻断样例的预期实体也计入漏检；不能将表内漏检数全部称为原文泄漏。与上轮不同上下文和运行时设置的结果不是单变量对比。

**需要修改或验证的方案。**

1. 恢复有效诊断后，按固定安全类别细分无效结果：位置越界、原文不匹配、字段覆盖、标签、截断等。
2. 优先降低小模型计算位置的负担：评估字段编号、类别、精确原文子串，由服务端定位的版本化协议。
3. 重复原文通过出现序号或上下文消歧；不允许跨字段猜测。原文不存在或歧义无法消除时阻断。
4. 如果继续由模型给位置，则明确唯一坐标单位，校验Unicode码点到字节的转换，减少输入中的冗余标注和输出负担。
5. 协议调整要同步提示词、schema、解析器、能力指纹、缓存版本与文档。不要在当前严格协议中悄悄加入猜测修复或静默丢弃。

**验收。** 除确定性的工程用例外，必须重跑固定语料及未参与提示词调整的独立语料，分别统计无效结果、额外阻断、放行漏检与误伤。先确定质量阈值，再测量，不能按跑出的结果倒推通过标准。

## 6. 第三批：控制误伤和复杂请求耗时

### F-04：姓名规则把技术词“程序”当成人名

**代码入口。** [rules.zh.yaml](../internal/routerredact/privacy_assets/rules.zh.yaml) 的 `conversational_chinese_person_primary`，当前参考行 27、29；关联规则检测和词典策略。

**复现。**

```text
输入：请通知程序和文档负责人明天提交。
出站片段：请通知<NAME:1>和文档负责人...
```

两种模型的组合检测均复现该误伤。新增规则中的“动作词＋姓氏＋汉字”把“程”作为姓氏，“程序”满足姓名形状。原来的版本号误判样例已通过，应保留，不应回退日期修复。

**需要修改。** 加入技术词、普通任务词、组织/角色称呼等负样本；根据上下文、候选边界和非人名信号收紧判定。确实不确定的候选可以交给有预算限制的语义复核，但不能只凭首字在姓氏表就断定为人名。不要用单一词语特判代替完整负样本验证。

**验收。** “程序”保持原样；“宁祁、陆遥、许澄、顾言、Élodie Durand、François Moreau”等当前正样例仍通过。继续加入独立姓名和任务文本，避免仅适配本次样例。

### R-05：复杂输入仍存在预算和失败原因不清的问题

**代码入口。** [runtime_redactor.go](../internal/routerservice/runtime_redactor.go) 的 `getGroupOrchestratorRedactor`、`groupLLMInvoker`；[manager.go](../internal/routerruntime/manager.go) 的 RedactionBudget 与调度；[detector_llm.go](../internal/routerredact/detector_llm.go) 的分块、生成及复核。

**本轮证据。** 4B原10条样例有4条阻断：

| 样例 | 耗时 | 对外错误 |
| --- | ---: | --- |
| 普通句子中的并列姓名 | 15,001ms | `redaction_extraction_failed` |
| 联系人、电话、邮箱 | 12,125ms | `redaction_extraction_failed` |
| emoji与重音字符姓名 | 5,114ms | `redaction_extraction_failed` |
| 跨分块长文本 | 15,011ms | `redaction_extraction_failed` |

其中两条接近15秒，但未取得能细分全部4条的原始响应/阶段诊断，因此不能将4条全部称为超时，也不能都归为格式失败。当前代码中组合 Pipeline 上限为30秒，普通 Manager 的默认脱敏预算仍为15秒。

**需要修改。**

1. 首先记录固定、安全的分阶段诊断：排队、加载、上下文检查、请求、生成、解析、每个批次及取消原因；不记录真实敏感原文。
2. 定义入口总截止时间和各阶段预算的关系，避免外层承诺30秒、内层按15秒提前结束而难以诊断。普通与实验模式的预算选择需明确，不能自动扩权。
3. 按实际 token 与预计实体输出规模分批，减少重复提示内容；重试和复核共享剩余总预算，不能每次续满。
4. 复用已有会话缓存，确认模型、上下文、规则、提示词和协议变化后正确失效。
5. 长文本保证完整覆盖、跨块边界处理和去重；任一必要块未完成时，不得以局部结果发送原请求。

**验收。** 在固定机器、模型、上下文和预算下比较原10条及独立复杂样例；记录P50/P95与各失败原因。达到约定预算内的成功标准，同时验证取消、超时和重试后槽位释放、无孤儿进程、无原文回退发送。
