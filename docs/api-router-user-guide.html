THE PRACTICAL GUIDE

让第一条 AI 请求跑通，
再学会端云协同。

从添加供应商到连接 WorkBuddy / Loomy，再把云端和本地模型组合成路由组。每一章都告诉你：去哪里、填什么、做完怎样确认。

开始配置 ↗直达端云协同离线可读 · 单文件 HTML

项目统一名称为“端云协同”。命令、发布包和配置路径沿用兼容的技术标识；旧版程序请升级后使用新名称。

STEP 01连上云端准备 API Key，保存供应商 STEP 02跑通应用选择模型，完成第一条请求 STEP 03组合路由添加主备模型，选分配策略 STEP 04升级端云协同安装本地模型，验证分流

第一次使用怎么读？

先完成第 1–3 章，确认一个云端模型能回答；再做第 4–6 章。只需要云端服务时，可以跳过本地安装与脱敏。

准备好这三样

已安装或已构建的端云协同、供应商签发的 API Key 与基础地址，以及已启动过一次的 WorkBuddy 或 Loomy。

目标：打开正确的管理页面，认识配置顺序。

打开管理页面

  1. 从你安装的位置启动 Router

    仓库用户：在项目根目录双击 start.cmd，或运行下面的 PowerShell 命令。发布包用户：使用安装目录中的 api-router.exe service start。

    powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/start-project.ps1 -NoBrowser

  2. 打开启动结果中的实际管理地址

    使用输出中的管理 URL / managementURL。服务默认尝试 127.0.0.1:13145，端口占用时会自动选择其他回环端口；以本次启动结果为准。

  3. 确认页面已连接本机服务

    页面会自动连接管理接口。若显示断开，先确认服务运行，再点击“立即刷新”。在“网关 / Gateway”中可查看服务与监听地址。需要中文时，到“设置 → 语言”切换。

你会看到的词它负责什么接下来怎么用
供应商 Providers提供云端模型的 API 平台保存 Key、地址与协议
模型 Model实际回答请求的模型选供应商账号有权限使用的准确模型 ID
路由组 Routing group把多个模型包装成一个调用入口按主备、权重或端云策略分配请求
Agent / 应用你实际聊天、写代码的宿主选模型或组，打开接入开关
本教程是独立教学页面。请在另一个窗口打开真实管理页操作；示意卡片和分流演示不会连接服务。管理令牌与供应商 API Key 用途不同。
02

配置第一个供应商

目标：把你有权限使用的云端模型加入候选列表。

供应商 → ＋ 添加供应商 → 选择平台 / 自定义供应商

  1. 选择已开通 API 服务的平台

    优先选择对应预设；列表中没有的平台可选“自定义供应商”。确认密钥所属平台和地区，例如不同千问平台、地域的 Key 不能混用。聊天产品的会员账号不等于 API 凭证。

  2. 填写名称、基础地址、协议与 API Key

    名称取一个方便识别的，例如“工作主用”。预设已给出的地址和协议，先核对再保留；自定义配置按供应商控制台或接口文档填写。

  3. 点击“保存”，查看模型列表

    保存后会尝试获取并缓存模型；也可能显示内置预设或缓存列表。获取模型失败不会撤销已保存的供应商。列表只是候选项，下一章用真实请求验证生成权限。

什么时候需要改代理和高级设置？

只有网络环境或上游接口要求时再改。系统代理使用运行环境的代理设置；“直连”绕过该代理；自定义代理需填写真实代理地址。请求头值必须为字符串，额外请求体不能覆盖模型、流式开关、对话或工具字段。不要在不清楚作用时复制其他平台的设置。

看到“已保存”还不算完成连接验证。模型列表能获取，也不代表每个模型都有生成权限。先接入应用发一条请求，再确认记录。
03

接入 WorkBuddy 或 Loomy

目标：让第一条云端请求成功返回。

Agent / Agents → 找到应用 → 选择路由组或模型 → 开启连接

  1. 先让应用生成配置，再完全退出

    如果从未启动过 WorkBuddy / Loomy，先打开一次，再结束任务并完全退出。这样 Router 才能检测配置目录，修改时也可避免应用同时覆盖配置。

  2. 在 Agent 页选择一个云端模型

    打开“选择路由组或模型”，按供应商或模型名搜索并勾选。第一次建议只选一个已开通模型。需要设为新会话默认时，用 ↑ / ↓ 把它移到 #1；改动自动保存。

  3. 打开该应用行右侧的连接开关

    等待“已连接”。Router 会把所选模型列表写入检测到的宿主配置；可以展开“详情”，核对模型列表与“新会话默认”。

  4. 重新打开应用，选择端云协同，再新建会话

    在应用自己的模型菜单选择端云协同供应商和刚才勾选的模型。发送下面这条简单请求，然后回 Router 的“用量 → 请求”刷新查看。

    请用一句话介绍你能帮我做什么。

WorkBuddy 操作重点

先结束正在运行的任务。接入后完全退出并重开 WorkBuddy，在新会话里切到端云协同的模型。旧会话可能仍使用此前选择。

Loomy 操作重点

同样重开并新建会话。若模型仍不对，检查项目级 .opencode 设置；出现扩展冲突提示时，先处理提示中的冲突再重新接入。

列表中没有想用的模型？在模型选择器里用 provider/model 添加自定义模型。其中 provider 是已保存的供应商 ID，model 是准确的上游模型 ID；不要用供应商显示名称猜 ID。
成功标准：应用收到正常回答，并且“用量 → 请求”出现对应的成功记录，实际模型与供应商符合预期。只有“已连接”不能证明上游调用成功。
04

配置路由组：先做一个主备组合

目标：让应用使用一个组入口，由 Router 决定实际模型。

路由组会对外提供一个 group/<id> 虚拟模型。应用选这个组，就可以按组内策略调度多个成员。先用两个已验证的云端模型练习，便于定位问题。

路由 / Routing → ＋ 新建路由组

  1. 填写名称并添加模型

    例如命名“日常助手 · 主备”，点击“添加模型”，选择主用云端模型与备用模型。可来自不同供应商，但都要有相应权限。

  2. 调整成员顺序，选择“按顺序”

    拖动或用上移 / 下移把主用模型排第一。发生可回退的失败或限流时再尝试后续成员。排第一的成员还决定本组对外报告的能力，请让主备能力与应用需求相匹配。

  3. 保存，记住组的真实调用标识

    保存后可在编辑器或组卡片查看、复制 group/<id>。中文显示名称和实际 ID 可能不同，请复制页面生成的标识。

  4. 回到 Agent 页，把应用改为选择这个组

    勾选新组，需要作为默认时移到 #1。确认连接有效，完全退出并重开应用，在新会话选择该组后再发送请求。

常用策略怎么选？

策略适合什么情况你需要做什么
按顺序有明确主用和备用把优先成员排前面；先保留默认超时与会话设置
轮流在多个健康成员之间分配请求加入可互相替代的模型，实际分配仍受健康与会话设置影响
按权重希望某些成员承担更多流量为成员设 1–100 的权重，例如 3 和 1 表示相对比例；短期未必恰好 3:1
手动暂时固定使用指定模型选择“当前生效”成员；需要切换时手动更改
智能 · 本地+云端根据请求与成员状态选择准备适合任务的成员；本地使用还需安装、开启与能力检查
端云协同本地处理适合的简单请求，云端处理更复杂请求先添加本地成员，再选此策略；详见第 6 章
进阶设置可以先不改，熟悉后再看
设置使用建议
模型列表固定为“只列出本组”。通过编辑器保存后，成员模型不再单独列出；在 Agent 中选择路由组即可使用组内模型。
上下文主备上下文差异大时，可选“最小模型的”以减少回退超长；对外报告更大窗口不会扩大成员的实际能力。
会话保持可能让后续请求继续使用同一成员。不要期待每一条消息都重新平均分配。
迟迟不出字 / 全都忙熟悉默认行为后再调。等待太长会增加延迟，太短可能打断慢速模型。
规则与模式规则按从上往下匹配，第一条命中生效。模式可自动加入匹配模型；嵌套组不能循环引用。
自动同名组跨供应商同名模型可能自动成组。点“固定为自定义”后再长期编辑策略。
最容易漏的一步：创建组后，一定回 Agent 选择该组。应用继续直连某个云端模型时，该组策略不会作用于它。回退也不保证每一种错误、每一种输出阶段都能重试成功。
05

安装并开启本地模型

目标：让一个本地模型真正处于可用状态。

本地模型 / Local model → 设备检测 → 选择模型 → 下载并安装 → 开启

本地模型是端云协同的前提。当前提供 Spark-X2.5 的 1.7B / 4B 两个档位；两者安装流程一致。按页面设备推荐和可用资源选择，不要只凭档位大小判断是否适合。

  1. 完成设备检测

    检查内存、磁盘与受支持的推理后端。检测结果是硬件建议；如果提示条件不足，先继续使用云端，或释放资源后重新检测。

  2. 选择 1.7B 或 4B，点击“下载并安装”

    等待模型、运行时依赖和文件校验全部完成。下载中断可按页面提示重试；支持继续下载时会复用已保存进度。

  3. 在“已配置的端侧模型”中打开模型开关

    开启后会选择并加载模型，执行本地能力检查；检查通过时尝试开启实验性判断与执行。等待加载结束，确认当前状态与提示，不能停在“已安装”就开始配置分流。

  4. 检查进程健康与实际推理后端

    查看“推理后端”，点击“检测进程健康”。检测到显卡不等于已使用 GPU；以实际后端和卸载层数为准。若页面显示能力检测或实验开关尚未通过，先按提示处理。

  5. 按需单独验证本地回答

    在 Agent 选择页面提供的 local/<model-id>，重开应用，在新会话发一条简短纯文本。到“用量 → 请求”确认本地执行成功，再把它加入路由组。

本地判断与执行目前属于实验性能力。功能检查通过不等于回答质量已正式验收。以真实任务的回答和请求记录判断可用性；本地慢或失败时，先查资源、健康与后端。
如何释放资源：关闭已安装模型的开关。模型开启后会保持加载，空闲时不自动卸载，下次启动会记住开关选择；只关闭网页不会停止 Router 或本地模型。
06

开启端云协同

目标：让适合的简单请求走本地，需要时走云端。

端云协同通过路由组策略启用。先确保一个云端模型已能正常回答、本地模型已就绪，再把两者放进同一组。

  1. 创建或编辑“端云助手”路由组

    到“路由 → ＋ 新建路由组”，添加一个已开启的本地模型，以及至少一个已验证的云端模型。新用户先用一个本地、一个云端即可。

  2. 加入本地成员后，选择“端云协同”

    只有组中有本地成员时才显示此策略。看不到按钮时，先检查是否真的添加了 local/… 成员。它与只把云端成员排顺序是不同的配置。

  3. 先将“本地模型脱敏”保留为“关”，保存组

    这样便于先验证分流是否正常。脱敏需要额外启动授权和单独核验，第 7 章再开启。

  4. 在 Agent 勾选“端云助手”，应用内也选它

    需要作为默认时移到 #1。确认连接，完全重开应用，新建会话，选择这个路由组。直接选择云端模型会绕过该组的分流。

  5. 分两种任务验证实际去向

    先试一句简短问候，再试复杂分析任务；如果应用支持，也可试带图片或工具的请求。每次都到“用量 → 请求”看实际模型、内部调用与失败阶段，不能根据答案风格猜去向。

练习 A · 简单纯文本“你好，请用一句话说明什么是 API。”
在本地可用且判断适合时，有机会由本地回答；宿主附带的系统提示、工具和历史也会影响最终分流。
练习 B · 复杂任务“请从可靠性、成本和性能三个角度分析一个多区域系统方案，说明取舍。”
这类任务更可能交由云端；请以实际请求记录确认。

动手理解：这条请求可能去哪？

教学模拟 · 不调用模型，不代表实际调度结果。修改条件，观察常见分流路径。

应用 → 端云路由组 → 本地云端
本地优先尝试 → 云端兜底

短小简单纯文本且本地就绪时，可先尝试本地；判断不适合或遇到可回退的失败时转云。最终结果以请求详情为准。

记住实际边界：本地繁忙或不可用，以及图片、工具、长上下文、复杂任务等情况可能直接转云。端云协同不会自动对云端内容脱敏；本地判断也可能带来额外延迟。
07

按需试用本地脱敏

可选进阶：在符合条件的转云请求前准备脱敏内容。

本地脱敏会尝试识别并替换敏感信息，云端回答后再还原占位符。它与“让本地模型回答”是两项能力，需要单独开启。

  1. 检查服务是否带实验性脱敏授权启动

    在“设置 → 服务管理”查看“启动时实验性脱敏”。如果未开启，先结束任务，在服务管理停止 Router，再用同一安装位置、同一配置目录的 EXE 重新启动，添加实验参数：

    # 将路径替换为“服务管理”中显示的当前运行程序完整路径
& 'C:\实际安装目录\api-router.exe' service start --experimental-redaction

    这是一条需替换路径的命令模板。页面停止后会断开，请使用重新启动返回的管理 URL。不要临时改用另一份测试 EXE 或其他配置目录。

  2. 开启本地模型，在目标组打开“本地模型脱敏”

    组内应包含本地与云端成员，第一个本地成员必须与当前开启模型一致。编辑组，把“本地模型脱敏”设为“开”并保存；确保 Agent 和应用实际选择的是这个组。

  3. 用虚构信息测试并查看脱敏记录

    例如“请把这条虚构联系人信息整理成一句话：姓名张小例，手机号 13800000000。”到“用量 → 脱敏”刷新、展开记录，比较原始输入、脱敏后输入和替换映射，并核对请求是否成功。

使用前了解这几项：识别质量尚未正式验收，可能漏检或误报。准备失败或超过共享的 30 秒预算会阻断转云；开启开关不能作为敏感信息绝不外发的保证。

对比面板展示最新一轮用户输入，不是完整出站报文或全部会话历史。本地观测记录包含原文和替换值，默认最多保留七天、500 个请求标识；需要清理时，在脱敏页点击“清空记录”并确认。关闭组内脱敏后，后续适用请求将不再经过此组的脱敏处理。

08

查看请求，确认配置真的生效

目标：分清“配置好了”和“请求成功了”。

用量 / Usage → 请求 / Requests → 刷新 → 点击一条记录
看哪里你要确认什么
状态与错误码是否完成请求；失败发生在鉴权、判断、本地执行、脱敏还是云端调用。
实际去向与模型最终是本地还是云端，具体使用哪个成员。显示路由组名本身不足以确认执行者。
尝试记录 / 内部调用主用是否失败、是否回退；本地参与了判断、执行还是脱敏。出现本地内部调用不等于最终由本地回答。
Token 与耗时上游实际报告的用量及请求耗时；未报告 Token 应视为未知，而不是零消耗。

一次完整核验怎么做？

  1. 记下本次选择的模型或组，发送一条容易识别的请求

    比如“请回答：这是一条端云测试。”避免在排错时混入太多并行任务。

  2. 刷新请求列表，按应用和时间找到记录

    展开记录，确认状态、去向与模型。若有多次尝试，查看最终结果，不要只看第一次候选。

  3. 到“用量 → 概览”看汇总

    这里只统计经过 Router 且处于保留窗口内的请求。参考价格与节省金额是估算，实际账单以供应商为准。真实云端测试可能产生 API 费用。

09

遇到问题，按现象排查

改一项、试一条新请求，再看一次记录。

供应商保存成功，为什么还是不能回答？

保存只代表本机配置写入成功。检查密钥所属平台 / 地区、API 地址与协议是否匹配、账号额度与模型权限，然后在应用新会话中重试。获取到模型列表也不能证明有生成权限。去“用量 → 请求”看具体错误。

Agent 提示没有模型，或检测不到宿主目录

先保存供应商，再在该 Agent 中至少勾选一个可用模型或组。宿主目录不存在时，启动一次应用生成配置，完全退出后重试；仍检测不出时，按接入配置命令帮助显式指定目录。

已经“连接”，应用仍用原来的模型

完全退出并重开应用，选择端云协同供应商与目标模型 / 路由组，再新建会话。Loomy 还需检查项目级 .opencode 设置。连接中修改了模型列表也要重开；显示“需要重新连接”时重新选可用模型并连接。

为什么找不到“端云协同”策略？

先把一个真实本地成员加入组，策略才会出现。若本地模型尚未安装或未就绪，先回“本地模型”页完成安装、开启和检查，再返回路由编辑器添加。

开了端云协同，为什么一直走云端？

先确认应用选的是该组。检查本地是否开启、健康、能力检查通过，有无忙或排队；宿主是否附带工具、图片、长历史或复杂系统提示。简单的可见消息不等于整个请求简单。查看请求详情中的实际去向、判断与内部调用。

本地模型下载失败，或运行特别慢

先按页面提示定位下载阶段，检查网络、代理、磁盘与校验结果，再点“下载并安装”重试。运行慢时看进程健康、可用内存、实际推理后端与卸载层数；检测到 GPU 不能证明使用了 GPU。必要时改用资源需求更低的档位或暂时走云端。

开启脱敏后请求被阻断

核对启动授权、组内第一个本地成员和当前开启模型是否一致；检查本地健康、错误码与“用量 → 脱敏”。准备失败或超时会阻断云端。若决定停用，明确将组内“本地模型脱敏”设为“关”，了解后续适用请求将直接按策略路由。

为什么“用量 → 请求”里没有这条消息？

确认应用选择端云协同、选中目标模型或组并使用新会话，然后手动刷新。没有经过 Router 的请求不会记录；同时检查筛选条件与时间范围。

管理页面打不开，或端口变化了

从正常安装位置或仓库 start.cmd 重新启动，使用返回的实际管理 URL。端口占用由服务自动换端口处理，不要终止其他端口监听者，也不要手改应用端点去匹配临时实例。已接入宿主的端点由正常启动流程同步；重开宿主以加载。

停用、还原与日常管理

你想做什么正确操作
停止应用经过 Router结束任务并关闭应用，在 Agent 关闭接入开关，或“详情 → 断开并还原”。确认恢复结果，再重开应用。
只释放本地模型资源到“本地模型”关闭已安装模型的开关。云端能否继续使用取决于应用选中模型或组的配置。
停止 / 重启 Router“设置 → 服务管理”中按提示确认页面会断开，再停止或重启。停止会保留宿主接入配置，需要继续用时从原入口启动。
设置登录自启到“设置 → 服务管理”查看运行程序与登录自启设置，再按需要启用。首次安装不会自动开启。
还原提示文件冲突先保留改动文件与宿主恢复记录，按提示处理冲突。不要直接覆盖不明配置或删恢复记录。
修改或删除供应商、模型和组之后，重新检查 Agent 中的已选项。无效引用可能需要重新选择并连接；不要以为删掉组只影响路由页。
READY FOR EVERYDAY USE

先跑通，再组合，最后用记录验证。

日常使用只需要：启动 Router → 打开应用 → 选择端云协同的模型或路由组。需要调整策略时再回管理页，遇到问题优先看请求详情。
